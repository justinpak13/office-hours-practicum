# T14 - Roster sync: syncRoster (endpoint C) with safeguards

## Summary

Add `KhouryAdminSyncService.syncRoster(course)`. It pulls endpoint C for one course and applies it in a single transaction: add or adjust memberships for existing users, remove people who dropped, add new CRNs, and skip on failure, stale data or suspicious mass removal.

## Context

**Depends on:** T12 (service file, `normalizeEmail`, `higherRole`, `khouryRoleToRole`).

### Why this work exists

Today OH learns who a user is and which courses they're in from one source: Khoury Admin's login push (`POST /api/v1/login/khoury_login`). Login is moving to Keycloak SSO (Justin's work). Keycloak only gives identity (email, name), not courses. So OH must **ask** Khoury Admin for course data through three small endpoints. Alex Grove (Khoury Admin) prefers these targeted queries over mirroring every section.

The real Khoury Admin API doesn't exist yet. Alex will deliver **synthetic JSON data** as a PR into `packages/server/khoury-admin-stub/data/`. A dev-only fake server serves those files. **Goal: OH works exactly as it does today, with the same screens and data. Only the data source changes.** When the real API exists, only a base URL changes.

### The contract (three endpoints)

| | Endpoint | Response |
|---|---|---|
| A | `GET /api/v1/instructors/{email}/section-groups?semester={code}` | `{ semester, section_groups: [{ id, name, crns: number[] }] }` |
| B | `GET /api/v1/users/{email}/courses?semester={code}` | `{ semester, courses: [{ section_group_id, role: "Professor" \| "TA" \| "Student" }] }` (highest role per group) |
| C | `GET /api/v1/section-groups/{id}/roster` | `{ id, name, semester, generated_at (ISO UTC), professors: Person[], tas: Person[], sections: [{ crn, students: Person[] }] }` |

- Person = `{ email, first_name, last_name }`. **Email is the only identity key.** NUID isn't available.
- Unknown person in A/B → empty list (not an error). Unknown group in C → 404.
- Section group `id` (for example `"sg_1001"`) is stable forever. Names and CRNs may change.
- Semester code `YYYYSS`, where Fall's year is the calendar year + 1 (`202710` = Fall 2026). SS: 10 Fall, 30 Spring, 40 Summer A, 50 Summer Full, 60 Summer B.

### Rules every ticket must respect

- **Sign-in only adds or upgrades** memberships. It never removes or downgrades anyone.
- **Only the roster pull (C) removes people.** It never creates OH accounts. It only updates people who have already signed in.
- **Manual overrides** (`UserCourseModel.override = true`): roster sync never removes them and never changes their role. If C confirms the same role, clear the flag.
- **Professors** are never removed or downgraded by roster sync.
- Role order: `professor > ta > student`.
- **A failed call (non-2xx, timeout, bad shape) is never treated as "empty".** On failure, keep the data OH already has.
- Email normalization: rewrite `@husky.neu.edu` → `@northeastern.edu`, lowercase, and look users up with `LOWER(email)`.
- **No new npm dependencies.** `@nestjs/axios`, `axios` and `@nestjs/schedule` are already installed.
- **Do not touch** `POST /login/khoury_login` or `LoginCourseService.addUserFromKhoury`. Justin owns that path.
- The dev login and the fake server must never run in production.
- Out of scope: Keycloak, the real Khoury Admin connection, withdrawn-student handling (team decides 11/16), and profile photos.

## Acceptance Criteria

- [ ]  Returns `RefreshRosterResponse`: `failed` "Course isn't linked to Khoury Admin yet" when `khourySectionGroupId` is null; `failed` "Couldn't reach Khoury Admin, kept the current roster" on a client error or 404 (no writes in either case)
- [ ]  `unchanged` when the roster's `generated_at` ≤ the stored `khouryRosterGeneratedAt`
- [ ]  **Never creates `UserModel` rows.** Only people who already have an account get memberships
- [ ]  A person in more than one list gets the highest role (for example TA + student → TA)
- [ ]  Non-override, non-professor members missing from the roster are removed
- [ ]  Override rows: role never changed and never removed; `override` cleared only when C lists the same role
- [ ]  Non-override rows follow the roster's role (may downgrade TA → student)
- [ ]  Professors are never removed or downgraded
- [ ]  **Safety brake:** if removals would exceed 50% of current non-override, non-professor members → `skipped` with no writes (exempt when that count is 0; exactly 50% applies)
- [ ]  New roster CRNs are added to `CourseSectionMappingModel`; existing CRNs are never deleted
- [ ]  `updated` only if a membership was created, changed or removed, or a CRN was added; otherwise `unchanged`. Saving the timestamp doesn't count
- [ ]  All writes are in one transaction; a mid-sync failure rolls everything back

## Implementation Notes

**Algorithm:**
```
if !course.khourySectionGroupId → failed
roster = client.getRoster(id); error or null → failed
gen = new Date(roster.generated_at).getTime()
if course.khouryRosterGeneratedAt && gen <= course.khouryRosterGeneratedAt.getTime() → unchanged
desired  = map normalizedEmail → highest role across professors / tas / all section students
users    = UserModel where LOWER(email) IN desired keys          (never create)
current  = UserCourseModel rows for course
eligible = current where !override && role != professor
toRemove = eligible where user's email not in desired
if eligible.length > 0 && toRemove.length / eligible.length > 0.5 → skipped
for each user: missing → create | override → clear flag if same role, else leave
               | professor → leave | else → set role = desired
delete toRemove; add missing CRNs; course.khouryRosterGeneratedAt = new Date(gen)
```
- **Transaction:** everything after the fetch runs inside `DataSource.transaction(async manager => …)`, and **every read and write uses `manager`**. The codebase uses Active Record (`Model.save()`, `.remove()`), and those calls bypass the transaction, so don't use them here.
- **Why CRNs are add-only:** `ProfileService.getPendingCourses` finds a registered course by A's first CRN. Deleting a CRN the roster dropped would make a registered course show as "pending" again.
- **Why never create users:** this keeps today's behavior (accounts are created at login) and respects Khoury Admin's concern about OH holding data on people who never use it.
