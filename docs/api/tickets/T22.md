# T22 - Keycloak users get Khoury Admin data

## Summary

When a Keycloak user is first created, and again at most once a day, run the Khoury Admin sync for them in the background: endpoint A by email and endpoint B with their NUID. The sync hangs off Justin's login with a one-line hook, and it takes the user his login already resolved instead of finding or creating one by email.

## Context

**Depends on:** T20 (data with NUIDs), T21 (Justin's login and `UserModel.nuid` in `api-config`).

### Why this work exists

Today OH learns who a user is and which courses they're in from one source: Khoury Admin's login push (`POST /api/v1/login/khoury_login`). Login is moving to Keycloak SSO through oauth2-proxy (Justin's work, PR #20). Keycloak gives identity only: a permanent `sub`, email, name and NUID. It doesn't give courses. So OH must **ask** Khoury Admin for course data through three small endpoints. Alex Grove (Khoury Admin) prefers these targeted queries over mirroring every section.

The real Khoury Admin API doesn't exist yet. **Alex won't send synthetic data, so we write it ourselves** in `packages/server/khoury-admin-stub/data/`, shaped exactly like his final schema (`OfficeHours-KhouryAdmin-Schema.pdf`, Nov 18). A dev-only fake server serves those files. **Goal: OH works exactly as it does today, with the same screens and data. Only the data source changes.** When the real API exists, only the base URL and token change.

### The contract (Alex's final schema)

Every call sends `Authorization: Token <key>` (from `KHOURY_ADMIN_TOKEN`).

| | Endpoint | Response |
|---|---|---|
| A | `GET /api/v1/instructors/{email}/section-groups?semester={code}` | `{ semester, section_groups: [{ id, name, crns: number[] }] }` |
| B | `GET /api/v1/users/{email}/courses?semester={code}&nuid={nuid}` | `{ semester, courses: [{ section_group_id, role: "Professor" \| "TA" \| "Student" }] }` (highest role per group) |
| C | `GET /api/v1/section-groups/{id}/roster` | `{ id, name, semester, generated_at (ISO UTC), professors: Person[], tas: Person[], sections: [{ crn, students: Person[] }] }` |

- Person = `{ email, nuid, first_name, last_name }`. `nuid` is a string (for example `"001234567"`); keep it as text so leading zeros survive. `first_name` is the preferred first name. `last_name` may be `""`.
- **B requires `nuid`.** Khoury Admin looks people up by NUID because Banner can't be searched by email. A request without `nuid` gets 400.
- Unknown person in A/B → empty list (not an error). Unknown group in C → 404.
- **Section group id** = `sg_` + 18 digits, always a string. The first digit gives the kind: `sg_1…` = a group set up in Khoury Admin (semester + group number); `sg_2…` = a course group (semester + course number + campus number), meaning all sections of one course on one campus that aren't in a set-up group, named like "CS 1800 London".
- **Groups can move.** If a course group's sections are later added to a set-up group, they move to that group's id, and the course group's id returns 404 once it has no sections left. OH re-links the course when a professor signs in (T19).
- `generated_at` is when Khoury Admin built the response. Data is read live from Banner, so A, B and C only agree when read at the same moment. It's not a "data changed" signal.
- Semester code `YYYYSS`, where Fall's year is the calendar year + 1 (`202710` = Fall 2026). SS: 10 Fall, 30 Spring, 40 Summer 1, 50 Full summer, 60 Summer 2.

### Identity (Justin's Keycloak model)

- A Keycloak user is the `UserModel` row with a matching `keycloakSub`. Justin's `OidcUserService.findOrCreate` creates it on first sight and keeps email, name and `nuid` in sync with Keycloak on every request. **OH never links a Keycloak user to an existing row by email.**
- `UserModel.nuid` is nullable, not unique, and excluded from responses. Users from the old Khoury Admin login have `keycloakSub = null` and usually no NUID. They're called **legacy rows** below.
- Emails are unique only among legacy rows (T21). A Keycloak user may share an email with a legacy row.

### Rules every ticket must respect

- **Sign-in only adds or upgrades** memberships. It never removes or downgrades anyone.
- **Only the roster pull (C) removes people.** It never creates OH accounts. It only updates people who already have an account.
- **Manual overrides** (`UserCourseModel.override = true`): roster sync never removes them and never changes their role. If C confirms the same role, clear the flag.
- **Professors** are never removed or downgraded by roster sync.
- Role order: `professor > ta > student`.
- **A failed call (non-2xx, timeout, bad shape, missing token) is never treated as "empty".** On failure, keep the data OH already has.
- Email normalization: rewrite `@husky.neu.edu` → `@northeastern.edu`, lowercase, and compare with `LOWER(email)`.
- **No new npm dependencies.** `@nestjs/axios`, `axios` and `@nestjs/schedule` are already installed.
- Justin owns the login code (`/login/khoury_login`, `OidcUserService`, `JwtStrategy`). Change it only where a ticket says so, and tell him first.
- The fake server must never run in production.
- Out of scope: the real Khoury Admin connection (URLs, network path, real token), withdrawn-student handling, and profile photos.

## Scope

## Acceptance Criteria

- [ ]  `syncIfDue(user)` starts a sync when `lastKhourySyncAt` is null or more than 24 hours old; otherwise it does nothing
- [ ]  The request never waits for Khoury Admin: the hook starts the sync and returns. A failure is logged and never fails the request
- [ ]  `lastKhourySyncAt` is set when a sync starts, so concurrent requests from one page load start at most one sync
- [ ]  Endpoint A runs by the user's email, exactly as T12 (section groups saved, CRN linking, T19 re-link)
- [ ]  Endpoint B runs with `user.nuid`. If `nuid` is null, B is skipped with a warning and A still runs
- [ ]  `getCourses` without a NUID throws `KhouryAdminError` before any request; the fake server returns 400 `{ "error": "nuid required" }` without `nuid`
- [ ]  Memberships from B follow T12's rules: add or upgrade only, never remove or downgrade
- [ ]  The sync never creates or looks up users by email; it only uses the user passed in
- [ ]  Cookie logins (`auth_token`, dev login) don't trigger the sync; only the Keycloak path does
- [ ]  Logging in through Justin's demo as `li.edwa@northeastern.edu` (NUID `000000008`) with the fake server running saves his section groups, and his memberships match the T20 data

## Implementation Notes

- Justin's `findOrCreate` runs on **every request**: oauth2-proxy sends the Keycloak token each time, and there's no single sign-in moment. That's why the sync is gated by `lastKhourySyncAt`.
- Claim the run with a conditional update (`SET lastKhourySyncAt = now() WHERE id = ? AND (lastKhourySyncAt IS NULL OR lastKhourySyncAt < now() - interval '24 hours')`) and only sync if a row was updated. This replaces T12's per-email advisory lock for this path.
- If the sync fails, keep the claimed timestamp: a Khoury Admin outage shouldn't cause a retry on every request. The next attempt is 24 hours later. Add `// NOTE: retry after 24h on failure; shorten if outages matter`.
- Keep T12's helpers (`normalizeEmail`, `higherRole`, `khouryRoleToRole`, `upsertMembership`, `logFailure`). Remove the find-or-create-by-email part of `onSignIn`; nothing else calls it once T13 is superseded.
