# T15 - Registration carries section group id and pulls roster

## Summary

Change `CourseService.registerCourses` so each new course gets `khourySectionGroupId` from the professor's section group, and run `syncRoster` right after registration so existing users land in the course without waiting.

## Context

**Depends on:** T11 (id on `KhouryProfCourse`), T12 (A writes ids into `ProfSectionGroupsModel`), T14 (`syncRoster`).

### Why this work exists

Today OH learns who a user is and which courses they're in from one source: Khoury Admin's login push (`POST /api/v1/login/khoury_login`). Login is moving to Keycloak SSO (Justin's work). Keycloak only gives identity (email, name), not courses. So OH must **ask** Khoury Admin for course data through three small endpoints. Alex Grove (Khoury Admin) prefers these targeted queries over mirroring every section.

The real Khoury Admin API doesn't exist yet. Alex will deliver **synthetic JSON data** as a PR into `packages/server/khoury-admin-stub/data/`. A dev-only fake server serves those files. **Goal: OH works exactly as it does today, with the same screens and data. Only the data source changes.** When the real API exists, only a base URL changes.

### The contract (three endpoints)

| | Endpoint | Response |
|---|---|---|
| A | `GET /api/v1/instructors/{email}/section-groups?semester={code}` | `{ semester, section_groups: [{ id, name, crns: number[] }] }` |
| B | `GET /api/v1/users/{email}/courses?semester={code}` | `{ semester, courses: [{ section_group_id, role: "Professor" \| "TA" \| "Student" }] }` (highest role per group) |
| C | `GET /api/v1/section-groups/{id}/roster` | `{ id, name, semester, generated_at (ISO UTC), professors: Person[], tas: Person[], sections: [{ crn, students: Person[] }] }` |

- Person = `{ email, first_name, last_name }`. **Email is the only identity key.** NUID isn't available.
- Unknown person in A/B → empty list (not an error). Unknown group in C → 404.
- Section group `id` (for example `"sg_1001"`) is stable forever. Names and CRNs may change.
- Semester code `YYYYSS`, where Fall's year is the calendar year + 1 (`202710` = Fall 2026). SS: 10 Fall, 30 Spring, 40 Summer A, 50 Summer Full, 60 Summer B.

### Rules every ticket must respect

- **Sign-in only adds or upgrades** memberships. It never removes or downgrades anyone.
- **Only the roster pull (C) removes people.** It never creates OH accounts. It only updates people who have already signed in.
- **Manual overrides** (`UserCourseModel.override = true`): roster sync never removes them and never changes their role. If C confirms the same role, clear the flag.
- **Professors** are never removed or downgraded by roster sync.
- Role order: `professor > ta > student`.
- **A failed call (non-2xx, timeout, bad shape) is never treated as "empty".** On failure, keep the data OH already has.
- Email normalization: rewrite `@husky.neu.edu` → `@northeastern.edu`, lowercase, and look users up with `LOWER(email)`.
- **No new npm dependencies.** `@nestjs/axios`, `axios` and `@nestjs/schedule` are already installed.
- **Do not touch** `POST /login/khoury_login` or `LoginCourseService.addUserFromKhoury`. Justin owns that path.
- The dev login and the fake server must never run in production.
- Out of scope: Keycloak, the real Khoury Admin connection, withdrawn-student handling (team decides 11/16), and profile photos.

## Implementation Notes

- **Ordering matters:** `registerCourses` creates the course, then the CRN mappings, then the professor's `UserCourseModel`. Calling `syncRoster` before the professor row exists makes the sync create a professor row, and registration then creates a duplicate.
- The existing flow stays the same: `ProfileService.getPendingCourses` → `/apply` wizard (`packages/app/components/Apply/ApplyPage.tsx`) → `POST /courses/register_courses` → `registerCourses` (matches by `sectionGroupName`, writes `CourseSectionMappingModel`).
